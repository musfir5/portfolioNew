I'm an Oracle PL/SQL developer and data analyst working inside Grand Hypermarket, one of Kuwait's high-volume, multi-branch retail operations. My job sits between the database and the business — I write the SQL and PL/SQL that keeps Sales, Purchase, Inventory, Finance and HR running on accurate numbers, and I build the Power BI dashboards and internal tools that put those numbers in front of the people making decisions.

Most of what I build starts the same way: a process running on spreadsheets, manual TOAD scripts, or someone's memory — and my job is to turn it into a system that's indexed, automated, and reliable enough that nobody has to double-check it. That's meant architecting a Star Schema data warehouse from scratch, automating purchase orders off live stock rules, and building the ASP.NET portals that store and field staff use every day.

I'm currently deepening my data engineering and BI skills — data modelling, ETL design and Python — while finishing my B.C.A. in Computer Applications.

01 / Data Engineering

Retail Data Warehouse

Problem — BI and executive reports pulled from inconsistent raw tables with no shared source of truth.

Architected a Star Schema warehouse using a Bronze → Silver → Gold layered approach, with ETL procedures, indexed views and Gold-layer reporting views covering five analysis types: change-over-time, cumulative, performance, part-to-whole and customer/product segmentation.

Impact — single source of truth for all BI; ~60% faster Power BI refresh
Oracle PL/SQLETLStar Schema
02 / Reporting Portal

Sales Loss Due to Out-of-Stock

Problem — Stores had no way to quantify revenue and profit lost to stockouts.

Built an ASP.NET Web Forms + Oracle portal joining stock-inconsistency data with product master, purchase order activity and daily stock-on-hand — drillable by Article, Department, Sub-Category or store-type summary, with a staff remarks workflow.

Impact — stockout loss now visible in real dollar terms, not guesswork
ASP.NET Web FormsOracle SQLAJAX
03 / Automation

Automated Purchase Order Engine

Problem — POs were created manually by planners watching stock levels — slow and inconsistent.

Built a PL/SQL procedure triggered by stock-level rules per article and location, generating purchase order logic automatically instead of relying on manual monitoring.

Impact — ~80% less manual PO effort across multiple branches
